# 协作与任务流转

## 一轮怎么推进

制作人确定一个可试玩目标 → 拆成少量任务 → 执行者认领并交付 → 程序集成 → 制作人 review、用户试玩 → 完成任务归档 → 再开下一轮。

通常一轮 3–6 项任务，每项尽量半天到一天能交付；超过一个工作日且可独立验证的部分继续拆开。不因等待用户试玩而阻止已授权的修复，不要求每份素材单独签字。

## 任务约定

- `plan/README.md` 是当前清单。任务文件放在 `plan/Rxx/programming/`、`art/`、`audio/`。
- 每项写清目标、依赖、范围、输入、输出位置、完成检查和交付记录。共享参数放在本轮 README，避免三个工种各写一套。
- 状态只用：待认领、进行中、待 review、受阻。通过 review 后移出 plan；不在待办中积累已完成文件。
- 认领时填写执行者并更新清单；已有执行者的任务不重复接。依赖未完成可准备独立部分，不能标记整体完成。
- 程序独占 `Game/` 的修改与资源导入；美术、音频先交到各自 `SourceAssets/`。不要多名执行者同时改同一场景、配置或 Unity 项目设置。
- 技术实现细节由执行者决定；调整玩法、扩大范围、换引擎版本时先向制作人说明影响。任务外发现的问题记录下来，不顺手扩建系统。

## 交付与 review

交付记录直接追加在任务文件末尾，包含：实际文件、打开／运行方法、做过的检查与结果、未完成项或偏差、待 review 问题。视频和截图是补充；可运行的任务必须实际运行，不能仅凭代码存在报完成。

程序工作未运行就如实写“未运行”和原因；资源写清哪些是实物文件、哪些仍是草图。美术与音频缺失时程序可先交占位试玩，但资源任务继续留在 plan。不得把占位资源说成已完成的 AI 资产。

制作人检查结果和范围，问题留在同一任务中修正。涉及用户体验的判断记录为试玩结论或待验证假设，不写成已经证实的市场判断。

## 归档

通过 review 后，制作人把任务移到 `archive/Rxx/原类别/原文件名.md`，保留要求、交付与 review 记录，并更新 plan 清单、归档索引和文件内链接。任务 ID 始终不变；跨任务依赖按 ID 引用。若本轮 README 尚未归档，已归档任务的说明链接暂时指回 plan 中的本轮文件，待整轮归档后再改回同目录引用。

本轮全部任务完成后，把本轮 README 一并移到 `archive/Rxx/README.md`，补充短结论：交付版本、实际问题、下轮选择。更新总体方案的当前迭代链接。代码、最终素材和构建留在各自工作目录，不随任务文件一起移动。

取消或延期的任务同样移出当前清单，并写清原因；归档不等于声称完成。尚未开展的后续版本只在总体方案留一句方向。

Unity 工程首次建成并运行后，由制作人询问用户是否创建 GitHub 仓库并提交；未得到指示前不创建远端或推送。当前仅整理文档，不算游戏工程已建成。
